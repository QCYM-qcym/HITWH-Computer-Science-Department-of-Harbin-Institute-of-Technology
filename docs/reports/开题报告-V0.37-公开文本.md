1．课题来源及研究的目的和意义

1.1 课题背景

随着视频播放、直播、网络游戏和云服务的普及，网络需要持续处理不同类型的访问请求。不同业务的流量变化并不相同：视频平台在热门节目播出时访问量增加，游戏服务在版本更新或活动开始后出现集中访问，云服务也会随用户工作时间和任务规模发生负载变化。这些变化属于正常业务活动，但在部分流量指标上，可能表现出与攻击相似的突然增长。

微软、腾讯、字节跳动等企业，其相关业务不仅需要保障服务能够承受正常访问高峰，还需要识别和处置恶意流量。网络流量异常检测不能只判断流量是否变大，还需要结合协议、端口及其他特征，分析当前变化是否偏离正常行为。例如，某一分钟的TCP流量计数较高，可能与正常业务增长有关，也可能与异常活动有关，仅凭这一项指标难以直接确定原因。

本课题以UGR16分钟级流量数据为研究对象，结合当前流量特征与近期变化开展异常检测[1]。拟通过对照实验，考察加入历史信息后能否减少正常流量波动引起的误报，并保持攻击识别能力。在此基础上，开发网络流量异常检测与分析系统，支持数据查看、检测任务执行和报警结果分析。

1.2 研究的目的和意义

本课题拟实现一套分钟级网络流量异常检测与分析系统，帮助用户查看异常发生的时间、相关流量变化及检测结果。系统总体架构如图1-1所示。图中保留各模块及工具的设计参考，实际开发先完成数据处理、检测和网页展示，具体工具按实现需要确定。



图1-1  系统技术架构

系统首先读取公开数据集中的分钟级流量特征，对时间、字段和标签进行核对，再按时间顺序完成数据划分与预处理。检测模块计算各分钟的异常分数，将超过阈值的分钟标记出来。网页端展示流量变化曲线、异常分数和报警时间，用户可以选中某个报警片段，查看相关特征及其近期变化，辅助分析报警原因。由于输入数据已经按分钟聚合，系统主要定位异常时间段，不直接定位某一条连接，也不将异常分数直接解释为具体攻击类型。

课题重点考察历史信息对检测的作用。自编码器可以学习正常数据的特征，并根据输入与恢复结果之间的差异辅助判断异常[3]。拟在当前特征之外补充近期流量变化，使模型能够参考当前数据所处的时间背景。历史信息能否帮助区分正常波动与异常活动，需要通过实验检验[2]。

研究以当前输入自编码器与加入历史信息的自编码器为主要比较对象，并使用隔离森林作为基础对照。各方法按相同的时间顺序划分数据，在验证阶段确定参数和报警阈值，测试阶段保持固定，比较正常流量误报和攻击漏报情况。

通过上述研究，形成能够导入数据、执行检测、查看报警和导出评价结果的系统；通过统一条件下的对照实验，明确历史信息在哪些场景下有帮助、在哪些情况下可能导致漏报或报警延迟，为后续方法调整提供依据。

2．国内外在该方向的研究现状及分析

2.1 国外现状及分析

随着网站和在线应用向云平台迁移，企业需要同时应对用户集中访问和恶意流量冲击。亚马逊、微软与谷歌陆续将流量监测及攻击防护接入云服务，保障业务持续运行。

2016年，亚马逊推出AWS Shield，与负载均衡、CloudFront内容分发网络及Route 53域名服务配合，为云上应用提供分布式拒绝服务攻击（DDoS）防护。其业务逻辑是在用户访问链路中检测和缓解攻击，减少恶意请求对网站及应用的影响。[5]

微软Azure DDoS Protection持续分析应用流量，依据业务画像调整防护配置。微软公布的案例显示，2021年8月，一家欧洲客户遭遇峰值2.4 Tbps的DDoS攻击，平台通过防护机制保障业务运行。该方案将业务平时的流量表现作为判断与防护的参考。[6][7]

2023年，谷歌公布了峰值每秒3.98亿次请求的HTTP/2攻击案例。谷歌通过边缘防护设施与针对性措施缓解攻击，并为采用负载均衡和Cloud Armor的客户提供相关保护。此类攻击通过密集请求消耗处理能力，说明检测除关注流量规模，还需分析协议行为。[8]

上述产品把检测与业务访问链路结合，并考虑应用自身的运行情况。流量监测逐步服务于攻击发现、告警调查和业务连续性保障。

2.2 国内现状及分析

网络游戏、视频直播和在线交易的发展，使国内互联网平台既要保障正常访问高峰，也要防范恶意流量。腾讯、字节跳动和哔哩哔哩围绕不同业务，开展了攻击防护与高负载保障实践。

腾讯云将游戏版本发布、重大赛事直播和电商大促列为DDoS防护场景。这些业务在特定时段需要持续承接用户访问，攻击可能造成连接失败或服务中断。其产品支持按需调整防护能力，使业务方能够结合日常运行和活动安排配置防护资源。[9]

字节跳动通过旗下火山引擎向外部企业提供云服务。其DDoS原生防护将游戏列为典型场景，为云上公网业务提供常态化网络层防护，并可联动高防服务应对大流量攻击。业务处理由日常监测延伸到攻击期间的流量防护，以维持服务器可用性。[10][11]

哔哩哔哩的公开实践体现了正常高峰下的流量分析。2024年S14赛事期间，直播团队记录前期比赛的在线人数与技术指标，预估后续比赛资源，并通过压测核验容量。2025年春晚直播保障中，团队模拟开播洪峰检验扩容、限流方案，核心播放服务采用双机房部署，异常时调整流量分配。这些案例属于正常业务保障，不能作为攻击检测效果的证据。[12][13]

上述业务共同要求识别流量变化的原因：高负载可能来自正常活动，也可能包含攻击。本课题拟结合当前特征和近期历史分析分钟流量，通过统一测试比较正常高负载误报与攻击漏报，并提供异常分钟和特征变化的回放。

4.  研究方案

4.1 拟采取的研究方法和技术路线

拟通过软件工程方法开展研究，首先分析系统需求，确定各模块的功能及调用关系，再完成数据结构和接口设计。在此基础上编写程序，分模块测试，最后进行前后端联调，根据测试结果修改和完善系统。

系统采用前后端分离方式，在本地计算机上运行。数据处理与检测程序使用Python编写，借助scikit-learn和PyTorch实现模型。前端使用Vue 3、TypeScript和Element Plus开发，通过ECharts展示流量与检测曲线。前后端通过HTTP请求和JSON数据交换任务信息，后端负责调用检测程序并保存结果。

开发使用Visual Studio Code，借助venv管理Python环境，使用Node.js、npm和Vite运行与构建前端。代码通过Git和GitHub Desktop进行版本管理，使用pytest检查主要功能。拟先完成数据读取到检测输出的基本流程，再接入网页并开展联调。各子系统的实现思路如下。

4.1.1 数据管理与特征处理子系统

数据管理子系统负责读取、检查和整理UGR16v3分钟级流量数据。每分钟对应一条记录，包含134维特征，表示满足特定协议、端口及流量条件的记录数量[14][15]。特征组成如图4-1所示。



图4-1  分钟观测与134维特征

数据处理主要包括以下步骤：

（1）读取数据：核对字段顺序、时间范围及标签对应关系，标记重复、缺失和不确定记录。

（2）划分数据：按时间先后划分训练集、验证集和测试集，分别用于模型训练、参数与阈值确定、最终评价。

（3）整理特征：对数值范围进行统一处理，处理规则根据训练数据确定，再用于验证和测试数据。

（4）保存结果：保存整理后的特征、时间范围及处理设置，标签单独保留，用于后续评价。

4.1.2 时间分析与历史特征构建子系统

时间分析子系统用于描述近期流量变化，为检测模型补充历史信息。拟先整理当前分钟之前的一段连续数据，得到近期流量的参考水平，再描述当前特征与该水平的差异。图4-2保留了这一思路的详细设计，正文着重说明处理过程，具体计算设置在后续开发与验证中确定。



图4-2  历史残差增强自编码器的检测流程

历史信息只取自当前分钟之前的数据。例如，同样是较高的访问量，连续一段时间都较高与短时间内突然升高，所处的背景有所不同。系统拟将这种变化信息与当前特征一起交给检测模型，辅助判断异常。

历史窗口拟先选择较短时间范围进行比较，再根据验证结果确定。当前分钟完成检测后才加入历史记录；遇到时间中断，需要重新积累连续数据。历史不足的记录单独标记，不与其他记录混合评价。历史变化本身不直接等同于攻击。

4.1.3 异常检测子系统

异常检测子系统根据输入数据计算异常分数，并将超过阈值的分钟标记为报警。拟使用scikit-learn实现隔离森林，使用PyTorch实现自编码器，重点比较只使用当前数据与加入近期历史信息两种方式。图4-3保留不同输入方式的比较，连续窗口模型作为参考，暂不作为本课题必须完成的功能。



图4-3  三种模型输入方式对比

隔离森林通过划分数据寻找与多数记录差异较大的样本[16]。自编码器先学习正常数据的特征，再尝试恢复输入；恢复结果与输入差异较大时，给出较高的异常分数。加入历史信息的模型沿用这一基本过程，重点检验补充历史变化后检测结果是否改善。

报警阈值根据验证数据确定，最终测试时保持固定。运行时保存模型、参数与评分结果，便于后续核对。检测结果用于指出异常时间段，攻击类型通过独立标签进行评价。图中的USAD来源于已有时间序列异常检测研究[4][17]，其具体实现留作后续学习参考。

后端负责接收网页请求、调用检测程序，并返回任务状态和结果。用户选择数据及检测方法后提交任务，后端记录任务信息并开始处理，网页随后查询进度。交互关系如图4-4所示，具体接口与运行方式根据本地开发需要确定。



图4-4  任务提交与结果查询时序

后端主要包含数据管理、任务执行和结果查询三个部分。数据管理提供可用数据及时间范围；任务执行记录运行、完成或失败状态；结果查询返回异常分数、报警记录并支持导出。检测程序与网页调用同一套处理逻辑，避免两处计算结果不一致。

4.1.6 对照实验设计

实验使用相同的数据版本和时间划分，各方法比较相同的有效分钟。在验证阶段确定参数与阈值，测试阶段保持不变。图4-7保留了历史、特征和数据表示三类比较思路，拟先完成历史信息的主要对照，其余作为条件具备后的补充检查。

（2）历史窗口对照：比较不同长度的历史窗口，查看正常流量变化是否容易误报，以及持续异常是否出现漏报或报警延迟。需要时补充部分特征组的比较。

（5）用户可以通过网页选择数据和检测方法，查看流量曲线、报警记录及相关特征变化。

（6）评价模块可以将检测结果与数据标签对照，统计误报率、召回率和F1等指标。

（7）系统可以对比不同方法和历史窗口的检测结果，并导出评价指标及报警记录。

7．研究过程中可能遇到的困难和问题，解决的措施
